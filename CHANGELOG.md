# Changelog

## v1 draft

- Chat digests get a home: `project/internal/chat/` holds one digest per channel per month (seven summary sections, dated bullets, internal only), indexed by a `chat-digests` manifest. New `chat-digest` schema; `validate.py` checks the sections and dates. From the first full populate run, where the playbook listed chat as a source but had no place to keep what was read.
- First split of the onboarding guide into repo files: Step 0 to Step 7, the Cowork and Codex paths, the dry run, joining a project, and the admin material.
- Step 0: added guidance on GitHub sign-in and the kind of token to create, with permissions and handling rules.
- A GitHub token may be pasted into an agent session until a GitHub connector is available. Nothing is blocked: the agent warns about the risks and prefers a fine-grained, single-repo token. This is carried through `AGENTS.md`, the README, the Cowork and Codex paths, the dry run and the decisions file.
- Fallback when no GitHub connector or plugin is available: keep a fine-grained token in a gitignored `local/github-token` file, with setup steps, a check, the risks, and the matching `AGENTS.md` rule.
- Harm-first rules from the first adoption run: never print any part of a token (classify from response headers); metadata calls can expose content; browser reads need a visible pane; verify replacement text before accepting it; create a repo without pushing and verify it is private before the first push. Step 4 now reads titles and IDs only, records read depth, and gains a permission audit for client-shared folders. The dry run gains four probes: rulesets, token type, private repo and synced folder.
- Only generic content goes into the playbook: every change is checked for project-specific names and details before a push, using a local deny-list that is never committed.
- Running projects get equal billing with new ones: the README asks "new, or already running?", and a new guide, adopting a running project, treats what the client already sees as a baseline of claims to check. Step 5 starts from the baseline, stamps its version in each proposal and gains a `superseded` status; Step 6 gains the baseline review, hub access and the Hours and Sprints questions.
- Steps 1, 2, 3 and 7 updated from the adoption run: one repo per project with phases inside, named `<client>-<project>-delivery`; connectors shown up front, the task tool verified by counting items, repos listed from the GitHub API, folder-scoped Drive lookups and an `api` read method; a two-tier roster with explicit readers, hub access and code owners; scheduled runs documented as draft-only, a shadow-cycle freeze window and an hours reconciliation prompt.
- New templates and files: `templates/hub-update-prompt.md`, `pm/decisions.md` in the starter folder, and `onboarding/session-readiness.md`. The starter `team.yml`, `registry.yml` and `project.yml` gain the fields the steps now ask for.
- Admin and decisions: equal billing for running projects, one repo per project, the repo location policy, scheduled runs moved from parked to documented as draft-only, free-plan consequences, and new PMO checklist items for permission audits, the restricted folder and projects with no exec.
- The deny-list belongs to each contributor and project; the playbook now reminds users to update it when they start a new project.
- Repo layout: the delivery repo has four function folders (`project/`, `product/`, `qa/`, `design/`), each with a client-safe `hub/` tier and an `internal/` tier, a content map saying which file feeds each Hub section, one file per release, dated snapshot copies with manifests, meeting transcripts with short summaries, a weekly refresh and a one-off backfill. `data/` and `pm/` are gone. New page: `onboarding/repo-layout.md`.
- Schemas: 23 JSON Schemas and `schemas/structure.yml`, the machine-readable content map. Every `hub/` file starts with a header (`schema`, `updated`, `covered_through`, `proposals`).
- Scripts, built and tested with `scripts/selftest.py`: `validate` (the hard gate), `count_prs`, `scan_visibility` and the pre-commit hook, `sync` (the single door: validate, branch, scan, commit, push, pull request), `check_writers`, `codeowners` and `new_delivery_repo`. `build`, `extract_from_page`, `check_render`, `refresh` and `upgrade_playbook` are planned, with their interfaces in `scripts/README.md`.
- Rules: validation is a hard gate; the Hub reads `hub/` only; compare by id, never by position; copies are snapshots; read summaries first; the hook is installed before `internal/` is populated; the repo is never older than the page.
- Steps: Step 4 reconciles the registry with the repos, finds sources named in chat and lists the access each needs; Step 5 starts with the content map and parses an existing page into proposals; Step 6 builds the Hub from `hub/` only and fixes the embedded block's fields; Step 7 syncs the repo in the same run as a publish and documents the weekly refresh and the meeting backfill. The starter's Hours page is off until Step 6 asks.
- Closed the gaps in the layout: `structure.yml` lists folders as well as files and is checked against the layout page; `validate` enforces the `hub/` file header and the copy, manifest and meeting-summary rules; the pre-commit hook runs the same scan as `validate`; new `redact.py` and `refresh.py` (the deterministic half of the weekly refresh); the runbook template is filled in; and the week rule is documented. A delivery repo can now run `scripts/selftest.py` too: `new_delivery_repo.py` takes `scripts/` from its own folder and keeps the starter in `playbook/templates/`.
- Delivery Hub template, built: `templates/delivery-hub/` with the page skeleton, the stylesheet (tokens, light and dark themes, every component), the client script (timeline chart drawn from the embedded data, page router, filters, copy buttons), the design spec (`design.md`) and a complete fictional sample project. `scripts/build.py` builds the page from the `hub/` files and `scripts/check_render.py` runs static checks on it. Settings go in an optional `hub:` block in `project.yml`.
- New data: `project/hub/sprints.yml` (the Sprints page's data, required only when the project uses formal sprints) and a `title` for each version in `versions.yml`.
- The self-test also covers building the page, the ways `check_render` must fail, the brand logo, the repo-versus-published-block rule, and the shipped sample, and works from inside a delivery repo.
- The Delivery Hub shows the CodingCops logo (light and dark) in the brand bar and footer by default, as on the hand-built page. The files are in `templates/delivery-hub/assets/`; the name and logo are trademarks the MIT license does not cover. A project can name its own logo files in `hub.brand`.
- Feedback loop: a private ledger in each delivery repo (`project/internal/hub-operations/playbook-ledger.yml`, schema `ledger`), `scripts/feedback.py` to log, time the offer, check a draft is generic, record approval and file the issue with `gh`, a manager guide (`onboarding/feedback.md`), the owner's triage routine (`admin/feedback-triage.md`), a revised issue template, and three agent rules. Nothing is filed without the person's approval of the exact text, and the check blocks names on the deny-list, secrets, finding and ticket numbers, emails, handles and internal addresses.
- Stage 1 lands as one pull request when a running project moves into the layout after Step 5: `validate` stays strict and there is no partial mode (layout rule 9 and the adoption guide).
- `new_delivery_repo.py` creates every Stage 1 folder in `structure.yml` up front, with a `.gitkeep` in each empty one, so no function has to create another function's folder. `check_writers.py` is unchanged.
- Connector content reaches `local/incoming/` through a chunked writer in `refresh.py` (`--write-part`, `--finish`), never by re-typing; the layout page gives the fetch path per connector, and a full backfill runs one subagent per batch.
- Adopting a running project: values a page does not show are marked unknown or `inferred: true` (capability items, security cards, milestones, week blocks). The flag is never rendered, and `validate` lists the files that hold one for the reviewer.
- `scripts/upgrade_playbook.py`, built: moves a delivery repo's `playbook/` and `scripts/` to a newer playbook version together, records it in `state.yml` and opens the pull request through `sync.py`. Its `--check` is a new preflight step that reports when the pin is behind the playbook's latest commit.
- Hub data model: every page label can now be kept when a page moves to the hub build. All new fields are optional, so existing delivery repos stay valid.
- Changes can be `design-only` or `project-setup`, with their own grey chips; the staging chip's text is set once in `hub.staging_label` and used in the legend and on every change.
- Changelog groups take an optional heading per area (`groups` in a release file); without one, the area id is made readable.
- `versions.yml`: an optional `page_status` (label and tone) overrides the derived status; the derived label now says "Staging and production" when a release has both, instead of "In production".
- `versions.yml`: an optional `section_id` keeps an earlier page's release anchors; the generated `v1-4` style id stays as an alias. `validate` fails when two releases share an anchor.
- `versions.yml`: a new `unreleased` status for the next version with changes already on staging. It is never the current version and shows as the next release on staging. Migration: a next version marked `planned` only to keep it from being current can be changed to `unreleased`.
- Try-it prompts take an optional `short_list` flag; `security.yml` takes optional `note_links` and `caveat_links`; `phases.yml` takes an optional timeline `explainer`.
- The client page no longer prints the team's week rule: it shows `rules.counting.client_text`, or a fixed sentence with the week-end day and time zone, in the chart note and the embedded block. The scan and `check_render.py` fail a built page that names one of the playbook's scripts.
- A week is named by its last day everywhere on the page ("Week ending 9 Nov"; the Monday when `week_ends: monday`): the stats, the chart's tooltips and table, and the last-week card (layout rule 12).
- Try-it prompts may leave out `category`; the page then shows no label instead of a stand-in.
- Timeline band labels: an optional `short_label` per phase and `gap_short_label` for the gap before it; without them a narrow band's name is cut from its start ("GAP BEF…"), never shortened to a made-up "P2".
- The local GitHub token file may also be read for the read-only GitHub calls the steps require (fetching private code repos, `count_prs.py --source gh`, deploy-run checks), with the same handling rules and the same once-per-session warning.
- New rule: a live secret found in a source is reported to the person by source and location, with a suggestion to rotate it, and never repeated or stored.
- New rule: an employee's HR details (immigration, pay, medical) found in copied material are left out of the copy, and `project/internal/withheld.yml` (schema `withheld`) records each omission by source and location, never the content (layout rule 14).
- Step 0 has a done-when that includes a non-empty `local/deny-list.txt`, and preflight warns while it is missing or empty.
- `sync.py`: on a detached HEAD (a worktree made from `origin/main`) it creates `<function>/<topic>` before committing, and a failed push prints `git push -u <remote> <function>/<topic>`. New `--title` (default: the first line of the commit message); `--base` stacks a pull request on another branch.
- `count_prs.py`: `--source gh` is the default, and it falls back to git with a warning that rebase merges can be missed. Without `--today` it counts up to the week ending in `state.yml`, never the run date, and ignores later merges, so a late run cannot move `covered_through`. The weekly prompt and the runbook pass `--today <week ending>`.
- `registry.yml`: `code.merge_branch` (the branch pull requests merge into) and an optional `code.deploy_branch`. Migration: rename `code.production_branch` to `code.merge_branch` when convenient; the old name is still read when `merge_branch` is absent, so nothing breaks.
- `feedback.py`: a title may start with any repository path, dotfiles included (`.gitignore: ...`). New `comment F-nnn --on <issue>` posts an approved draft as a comment on an existing issue, runs the same check and records the comment link (ledger status `commented`); `mark --issue` accepts comment links.
