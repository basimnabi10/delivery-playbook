# Delivery Hub design

How the Delivery Hub looks and why. The page is generated by `scripts/build.py` from `page.html`, `hub.css` and `hub.js`, so this spec describes what those files already do, and what a change to them must keep. Build the sample (`python3 scripts/build.py --sample --out /tmp/sample-hub/index.html`) and open it to see everything described here.

## Principles

1. **Written for the client first.** Plain headings, short sentences, what changed for them. Everything on the page is safe for the client to read, because the Hub has one audience.
2. **Scannable before it is readable.** A contents list, a table of every release, and a last-week card come before the detail. A reader should know the state of the project in under a minute.
3. **Honest about where things are.** Every change says which of the project's environments it is in (by default production, staging or internal testing). Dates that are inferred say so. Counts that are partial say so.
4. **Generated, never hand-edited.** A wrong number is fixed in the data file and the page rebuilt. The design lives in the template, so every project looks the same.
5. **One file, no dependencies.** One HTML file with inline CSS and script. The only things it loads from outside are two font hosts.

## Page anatomy

Top to bottom on the Release notes page:

| Part | What it is | Data |
| --- | --- | --- |
| Skip link, brand bar | A "Skip to content" link, then the CodingCops logo (185 by 30) and a small tag | `project.yml` `hub.brand` |
| Page navigation | Release notes, Sprints, Hours. Shown only when there is more than one page | registry and project switches |
| Masthead | Eyebrow, two-tone title, one-paragraph lede, five meta cards (current version, covers, environment, last updated, prepared by), three principles, and a legend of tags | `versions.yml`, `state.yml`, `project.yml` |
| What's inside | A numbered contents list linking to each section | the sections present |
| At a glance | A table of every release, newest first: version, period, title, status, change count | `versions.yml`, `releases/` |
| Worked on / merged last week | One card with Shipped, Decided in the weekly sync, Next, and Waiting on the client | the latest `weeks/` file |
| 01 What the product does today | Cards by area, each a short list | `capabilities.yml` |
| 02 Delivery timeline | Five stat cards, the timeline chart, its legend, a milestone list, a data table | `phases.yml`, `milestones.yml`, `weekly-prs.yml` |
| 03 Security and data handling | Cards, then an optional note (green) and caveat (amber) | `security.yml` |
| 04 Release history | A toolbar (search, area, type, expand all), then one block per release, newest first | `releases/`, `qa/hub/` |
| Footer | Brand, "product, prepared for client", three short notes | `project.yml` |

Sprints and Hours are separate pages in the same file, reached with `#sprints` and `#hours`, and each has one numbered section. With no script, all pages show one after another.

Sections that have no data are left out and the numbering closes up. Nothing is padded.

## Tokens

All colour, type and spacing come from custom properties on `:root` in `hub.css`. Change a token, never a hard-coded value.

**Colour (light, then dark).** Dark values apply automatically with the system setting, and can be forced with `data-theme="dark"` or `"light"` on the root element.

| Token | Light | Dark | Used for |
| --- | --- | --- | --- |
| `--bg` | `#F6F7FC` | `#0E1222` | Page |
| `--surface`, `--surface-2` | `#FFFFFF`, `#FBFCFF` | `#151A2E`, `#181E34` | Cards, table stripes |
| `--fg` | `#131625` | `#EEF0F8` | Headings, strong text |
| `--text`, `--muted` | `#3A3F52`, `#5A6178` | `#CFD4E6`, `#98A0BA` | Body, secondary |
| `--heading` | `#2C3C82` | `#C3CDFF` | Title, large numbers |
| `--line` | `#E1E5F2` | `#273050` | Borders |
| `--primary`, `--primary-soft` | `#4156AF`, `#EEF1FB` | `#8EA0F0`, `#1D2547` | Links, numbers, chart bars, table headers |
| `--green`, `--green-soft` | `#2E9C4B`, `#E7F6EC` | `#5BCB7C`, `#12291C` | "New", "go" accents, the gradient's end |
| `--amber`, `--amber-soft` | `#9A6A1C`, `#FBF1DE` | `#E2B05A`, `#2B2111` | Staging, fixes, caveats, gaps |
| `--teal`, `--teal-soft` | `#2F7F62`, `#E3F2EC` | `#5FC7A0`, `#11281F` | Production, design, first phase |

**Type.** Space Grotesk for display (titles, numbers, card headings), Inter for body, IBM Plex Mono for labels, dates, counts and tags. All three come from Google Fonts, each with a system fallback stack. Scale: `--step--1` 0.8125rem, `--step-0` 0.9375rem (body), `--step-1` 1.0625rem, `--step-2` fluid 1.4 to 1.85rem (section titles), `--step-3` fluid 2.2 to 3.1rem (page title). Labels are mono, uppercase, letter-spaced, 0.625 to 0.75rem.

**Shape.** Cards have a 1px `--line` border and a 10px radius (12px for the chart). The page is one column, 900px at most. A 3px accent bar on the left of a card marks its tone: primary for information, green for progress, amber for caution.

**The signature.** Each numbered section opens with a large indigo number and a 3px vertical rule that fades from `--primary` to `--green`. A release repeats it with the version as the number. Section labels begin with `//` in mono.

## Components

- **Status pill.** Mono, uppercase, with a dot. Its colour follows the project's environment order (`environments.set`): the first environment teal, the second amber, the third primary, the rest and planned grey. A label set in `versions.yml` (`page_status`, with a tone) wins, and with `releases.status_label: manual` it is the only label. Otherwise it comes from the changes: the first two environments together read "<second> and <first>" ("Staging and production"); else the furthest environment's `client_label` ("In production", "On staging"). An `unreleased` version reads "Next release" plus the second environment's label and is never the current version.
- **Tags.** New (green), Improved (primary), Fixed (amber), Design (teal), Note (grey). Any other tag word is shown in grey.
- **Environment chips.** Outlined, in the same colours by order: by default Production (teal), Staging (amber), Internal testing (primary), Design only and Project setup (grey). Always beside the tag, never instead of it. The labels come from `environments.set`; the staging text can also be set with `hub.staging_label`. The legend shows the environments the changes use. A principle about how changes move through the environments appears only when an environment has a `deploy_note`, or in `hub.principles`; nothing about staging and production is printed by default.
- **Last-week card.** Green left bar. Parts have mono `//` headings. A link at the bottom goes to the current release.
- **Capability card.** A dot, the area name, then lines marked with `›`. A beta item carries a grey "Beta" tag. Planned and off items are not shown.
- **Timeline chart.** An optional `explainer` in `phases.yml` replaces the default introduction above it. Drawn in the browser from the embedded data block as SVG. Phases are shaded bands with a labelled strip on top, alternating teal and primary. A gap between phases is amber. A band's label is its full name when it fits, else the phase's `short_label` (or `gap_short_label` for the gap before it) from `phases.yml`, else the name cut from its start with an ellipsis ("GAP BEF…"), never an invented abbreviation. The current phase splits at today into elapsed (solid) and time remaining (hatched green). Bars are pull requests merged per week; a partial week is faded; the busiest week shows its number. Milestones are vertical lines with numbered dots on two rows, hollow when still in the future. A dashed line marks today. A tooltip shows on hover and on keyboard focus, one stop per week. Weeks are named by their last day ("Week ending 9 Nov") in the tooltip, the table, the stats and the last-week card. The note under the chart gives the week in one sentence: `rules.counting.client_text`, or the week-end day and time zone. Below it sit a legend, a numbered milestone list and a collapsible data table with the same numbers.
- **Security card.** A mono title, a short paragraph and a "Verified" date. The note is green and the caveat amber, both full width. Each can carry links (`note_links`, `caveat_links`), for example the environment addresses, when the project has decided the client may see them.
- **Toolbar.** Search, area and type filters, and an expand-all button. A live line says how many changes are showing. Releases with no match hide; matching changelogs open.
- **Release block.** Its anchor is the version id (`v1-4` style), or `section_id` from `versions.yml` to keep the links an earlier page used; the generated id then stays on the release head as an alias. Version in large display type, month and date range under it, a title with a gradient rule, a status pill. Then highlights, a collapsible detailed changelog, a notes grid, try-it prompts and an in-progress box.
- **Changelog.** Grouped by area. A group's heading comes from the release's `groups` list (area plus heading), else from the area id made readable (hyphens become spaces, first letter capitalised). Each row: tag and environment chip, text, references in mono underneath, and the date on the right. The header counts the changes.
- **Notes boxes.** "For IT and admins" has a primary bar; "Known limitations" an amber one, with a green "Resolved in vX" chip when a limitation has been closed.
- **Try-it box.** Green bar. Prompts marked `short_list` show open and the rest sit under "more prompts"; with none marked, the first three show. Each has a Copy button and a line saying what a good answer does, led by the prompt's category when it has one.
- **Sprint card.** Name, dates, goal, Delivered and Carried over lists, and the pull requests merged in weeks that end within the sprint.
- **Hours page.** Total and role count, a bar per role, a note on the basis (logged or allocation), and a table by week. No names, rates or budgets.

## Responsive and themes

- One breakpoint at 680px. Below it: section heads and release heads stack, the changelog row becomes tag and date on one line with the text under it, the contents list drops its subtitle column under the title, the chart is 270px tall, and the page navigation spreads full width.
- The root and body respect the device's safe-area insets, so nothing sits under a notch or a system bar.
- Tables scroll sideways inside their own container; the page never scrolls sideways.
- The logo has a light and a dark version (`assets/logo-light.png`, `assets/logo-dark.png`, 443 by 72 pixels so they stay sharp), swapped with the theme. It is shown at 185 by 30 in the brand bar and 111 by 18 in the footer. With one logo file, that file is used in both themes. A project with a different brand and no logo files gets a text wordmark with a green dot.
- Print: the toolbar, navigation and buttons are hidden and changelogs print open.

## Accessibility

- Text and tag colours are chosen for contrast against their soft backgrounds in both themes. Meaning never rests on colour alone: tags, chips and pills all carry words.
- Landmarks: a skip link, `main`, a labelled `nav` for the contents and for the pages, and `footer`. Each section is labelled by its heading. One `h1`.
- Every control has a visible focus ring (`:focus-visible`). The chart's weekly targets are focusable and announce their value. The chart has a text alternative, and its numbers are also in the data table.
- Filters announce the number of results. Motion is reduced when the system asks for it.

## Content rules

- Headings and labels are plain language. Dates read `13 Nov` in lists and `Nov 2026` for a period. Use curly apostrophes (’); the build converts straight ones.
- A highlight says what changed for the reader, in one or two sentences, with the lead-in in `**bold**` when it helps.
- Never on the page: credentials, internal links or addresses, developer names, test pass rates, budgets, rates or any money amount. The build's scan and `check_render.py` look for these.
- Write a limitation as what does not work yet, not as an apology, and close it with "Resolved in" when it is fixed.
- A try-it prompt is something a client can paste and run today, with what a good answer does.

## What not to change without a reason

- Do not hand-edit the generated HTML, and do not add a section that has no `hub/` data file. Add the file and its schema first.
- Do not add an external script, image or font host. The page may load only from the two Google font hosts.
- Do not put hours, rates or commercial figures on any page. The Hours page shows role-level totals only.
- Do not break the router: the only hash values are page names (`#sprints`, `#hours`) and element ids such as `#v1-1`.

## Changing the design

Edit `hub.css`, `hub.js` or `page.html` in the playbook repo, through a pull request. Then run `python3 scripts/selftest.py`, build the sample and open it in a browser at desktop and phone width, in light and dark, and with the keyboard. Update this page if a token or component changes.
